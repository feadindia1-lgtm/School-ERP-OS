# CRM + Admissions — Architecture (Prompt 2)

## Overview
CRM (**Front Porch**) sits inside the existing School Console shell. Every record is tenant-scoped and enforced server-side.

## Collections
- `crm_leads` — inquiries with pipeline `stage`, priority, source, assignment
- `crm_activities` — timeline entries (auto + manual)
- `followups` — pending / completed tasks with due date
- `campus_visits` — scheduled visits, staff double-booking prevented
- `admission_applications` — application state-machine
- `admission_documents` — per-application document rows with status
- `admission_conversions` — one row per successful application → student conversion
- `admission_settings` — per-tenant stages, sources, priorities, doc types, guardrails
- `students`, `guardians` — minimal stubs created at conversion (extended by future Student Master)
- `counters` — tenant-scoped sequential numbering

## Numbering
`INQ-YYYY-NNNNNN` (leads) · `ADM-YYYY-NNNNNN` (applications) · `STU-YYYY-NNNNNN` (students).
Generated by atomic `findOneAndUpdate` on `counters` collection — concurrency-safe.

## Pipeline
Stable stage codes: `NEW_INQUIRY → CONTACTED → VISIT_SCHEDULED → FORM_FILLED → UNDER_REVIEW → APPROVED → FEE_PENDING → ADMITTED · LOST`. Configurable per tenant via `/school/crm/settings`.

## Application state machine
```
DRAFT ─▶ SUBMITTED ─▶ UNDER_REVIEW ─▶ APPROVED ─▶ CONVERTED
         │           │      │      │
         ▼           ▼      ▼      ▼
      WITHDRAWN  DOCUMENTS_PENDING  REJECTED
```
`APP_TRANSITIONS` (backend) rejects invalid moves with 409.

## Approval guardrail
`admission.approve` requires all `required` doc types verified — bypassable only with `admission.override` permission (writes `admission.override` audit).

## Conversion (`services/conversion.py`)
Idempotent. On repeat call, returns existing conversion (`already_converted: true`). Creates `StudentStub` + `GuardianStub` and marks application `CONVERTED`. Full Student Master lands in a later prompt.

## Documents
- Storage: `LocalFilesystemStorage` under `/app/storage/tenants/{tenant_id}/documents/{doc_id}`.
- Access via authenticated `GET /school/admissions/applications/{id}/documents/{doc_id}/download` — cross-tenant reads fail with `PermissionError` inside the storage layer.
- Uploads: multipart, 10 MB max, MIME whitelist (PDF, JPEG/PNG/WEBP, MS Word).

## Permissions (new)
`crm.view · crm.create · crm.update · crm.delete · crm.assign · crm.activity.create · crm.activity.view · crm.stage.manage · crm.config`
`admission.view · admission.create · admission.update · admission.review · admission.approve · admission.reject · admission.convert · admission.override · admission.document.view · admission.document.upload · admission.document.verify`

## API surface — `/api/v1`
- CRM: `POST/GET/PATCH/DELETE /school/crm/leads`, `POST /leads/{id}/assign · /stage · /activities · /followups`, `GET/PATCH /followups/{id}`, `POST/GET/PATCH /visits`, `GET /leads/check-duplicate`, `GET /dashboard`, `GET/PATCH /settings`.
- Admissions: `POST/GET/PATCH /school/admissions/applications`, `POST /applications/{id}/status`, `GET/POST /applications/{id}/documents`, `GET /documents/{id}/download`, `POST /documents/{id}/verify`, `POST /applications/{id}/convert`.

## Tenant isolation
Every query filters by `user["tenant_id"]` derived from the authenticated JWT. Cross-tenant tests (iteration 5) verified 404 without leaking existence, dashboard counts scoped, and document download blocked at the storage layer.
